## Метод

1. По колонке `SubAgent` выделили эталонные классы и рассчитали квоты для 90 тестовых строк методом наибольших остатков с минимумом в один запрос на класс.
2. По формулировкам запросов внутри каждого класса вручную выделили семейства по смыслу, масштабу и сложности задачи. Например, у `talent-research` краткий поиск по названию роли и поиск по развёрнутому брифу образуют разные страты. У `hrp-analytics` отдельно представлены ссылки на сервисы, специализированная аналитика и многошаговые HR-запросы. В столбце `family` записано семейство каждой строки. При разметке использовали текст запроса и эталонный сабагент.
3. 37 выявленных групп близких переформулировок и расширенных вариантов одного запроса (83 строки) поместили целиком в одну выборку. Это относится и к трём группам, где близкие формулировки получили разные эталонные метки. Идентификатор группы в `near_duplicate_group` — минимальный `bucket_row` среди её членов. Среди запросов нет полных повторов после нормализации Unicode, регистра, пробелов и конечной пунктуации. Более широкое тематическое сходство между выборками ожидаемо при стратификации по темам.
4. В пределах квот выбрали разбиение, при котором больше всего семейств представлены с обеих сторон, затем минимизировали отклонения семейных квот от 30%. При равноценных вариантах использовали детерминированный порядок с SHA-256 и значением `20261126`.

51 из 53 страт присутствует в обеих выборках. В train целиком оказались два близких варианта запроса о переработках своей команды (`vacation`, `overtime-team`) и единственный запрос о публичных выступлениях руководителя (`hrp-analytics`, `external-public-executive-appearance`). Присутствие этих страт в обеих выборках потребовало бы разделить близкую пару или продублировать запрос. Для `outstaff` метрика на test основана на одном запросе.

## Воспроизведение

`manifest.csv` фиксирует принадлежность каждого запроса. `bucket_row` — номер CSV-записи после заголовка, начиная с единицы. При чтении следует использовать CSV-парсер с поддержкой переносов строк внутри кавычек. Чтобы восстановить выборки, сопоставьте исходные записи по `bucket_row`, отберите строки по `split` и сохраните их в порядке исходной корзины с её заголовком. В `train/bucket.csv` и `test/bucket.csv` сохранены все десять исходных столбцов и значения ячеек.

## Сопоставление трейсов с запросами

Для каждого JSON взяли полное сообщение пользователя из `attributes.llm.input_messages` корневого спана `LangGraph`. Сверили его с сообщением `human` из `attributes.input.value` того же спана, затем нашли точное совпадение с колонкой «Вопрос в новой корзине». Все 299 текстов совпали посимвольно и дали пары один к одному. Дополнительно сверили UUID в конце имени файла с `message_id` и `lookup` внутри каждого JSON и проверили уникальность `trace_id`.

В каждой выборке `trace_map.csv` связывает номер исходной CSV-записи (`bucket_row`) и номер записи в `bucket.csv` выборки (`subset_row`) с файлом в `traces/`. В обеих папках лежат копии исходных JSON с сохранёнными именами и проверенными SHA-256.

## Счёт вызовов для as-is

Вызов фиксировали по спану `TOOL task` верхнего графа. Имя из аргумента `subagent_type` совпало с именем дочернего спана исполнения во всех 546 вызовах. Обычно дочерний спан имеет тип `CHAIN`, а в 11 вызовах `agentic_skills` — `AGENT`. Вызовы упорядочили по времени старта `task`. Для каждого трейса тот же порядок получился по времени старта дочерних спанов.

В список вошли повторные вызовы, вызовы `general-purpose` и 23 фактических запуска, завершившихся ошибкой. `accuracy@1` сравнивает первый вызов с `SubAgent`, а `accuracy@full` проверяет наличие `SubAgent` среди всех вызовов. Запросы без вызовов получили 0 по обеим метрикам и входят в знаменатель.
