# Источник и вход

Инструмент search_persons, MCP-сессия recruiter. REST-эквивалент:
GET /recruitment/api/v1/persons/search/. Агент вызывает зарегистрированный инструмент,
не собирает HTTP-заголовки, не просит токен и не вызывает REST вручную.
Не использовать mcp_query/employee_actual для поиска, проверки или обходного пути.
Если search_persons недоступен, сообщить об ошибке подключения инструмента и остановиться.

Из пользовательской фразы извлеки ФИО либо табельный номер, без слов про эффективность.
Не выдумывай имя и отчество. При неясной форме фамилии попроси уточнить написание.
Сохрани ведущие нули табельного номера. По одному UUID поиск не поддержан контрактом:
попроси ФИО/табельный номер, кроме продолжения с уже подтверждённым personUuid в истории.

```json
{
  "query": "<ФИО_ИЛИ_ТАБЕЛЬНЫЙ_НОМЕР>",
  "page": 0,
  "size": 1
}
```

Заменить заполнитель перед вызовом. Всегда page=0 и size=1. Не увеличивать размер,
не перелистывать страницы, не добавлять filters, columns, metrics или parameters.
size=1 ограничивает число возвращённых записей, но не гарантирует уникальность поиска.

# Разбор ответа

Если MCP вернул текстовый JSON, разбери JSON в content[].text; если возвращён
структурированный ответ, используй его. Дальше разбирай документ известной формы:
error, result.success, result.data.persons. Не угадывай иную схему ответа.
MCP isError=true, error != null или result.success != true означают ошибку,
а не отсутствие человека. Сообщи о невозможности поиска, не повторяй неизменный вызов.
При отсутствующих обязательных полях либо неверных типах сообщи о нарушении контракта.
persons должен быть списком. Пустой список: «По этому запросу сотрудник не найден.
Уточните ФИО или табельный номер». Более одной записи при size=1 — нарушение ожидаемого
контракта; не выбирай одну произвольно.

При одной записи candidate = result.data.persons[0]:
- UUID: candidate.personUuid (непустая строка корректного UUID).
- ФИО: candidate.pbasic.fullName; части имени доступны в pbasic.lastName/firstName/midName.
- Табельный номер для сверки: candidate.jbasic.employeeId.
- Статус: candidate.jbasic.status; дата увольнения: candidate.jbasic.firedDate.
- Должности: candidate.jposition.position[].fullName.
- Подразделения: candidate.junit.unit[].fullName.
Массивы должностей/подразделений могут быть пусты или содержать несколько элементов;
не объявляй первый элемент единственной или основной должностью без такого признака.
Отсутствующие необязательные сведения не выдумывай.
Дату рождения, контакты, privacy-настройки не использовать для инсайта и не выводить.

# Проверка выбранного человека

Сверь ответ с введённым ФИО (без различия регистра, лишних пробелов, е/ё)
или с точным табельным номером. Совпадение только имени/отчества при другой фамилии
не подходит. При несовпадении не переходи к метрикам: попроси уточнить человека.
Если пользователь назвал полное ФИО и оно совпадает либо совпал точный табельный номер,
используй кандидата. Не утверждай, что в системе нет других однофамильцев.
Если указана только фамилия/часть ФИО, покажи найденные ФИО, должность и подразделение
и спроси: «Вы имеете в виду этого сотрудника?» До подтверждения метрики не запрашивать.
«Да» после такого вопроса подтверждает человека, а не переключает структуру на Agile.
При отказе попроси полное ФИО/табельный номер и сделай новый поиск только с уточнённым query.

Для текущего сценария нужен статус «активный» и отсутствие даты увольнения.
Если статус отсутствует, неактивный или сведения противоречат друг другу, остановись
и сообщи о необходимости уточнения. Например, активный статус вместе с подразделением
«Увольнение» не позволяет уверенно выбрать действующего сотрудника.
Активный статус и должность сами по себе не доказывают наличие роли руководителя
или прав пользователя на его показатели. Авторизация выполняется платформой отдельно.

# Выход

После подтверждения:
employee_full_name = candidate.pbasic.fullName
person_id = candidate.personUuid

Это согласованный контракт сценария: personUuid без преобразований передаётся в
filters.value при filters.column=person_id всех запросов dm_core.employee_hist.
Не подменять его jbasic.employeeId, unitId, positionId, UUID технической учётной записи
или ранее найденного человека. Историю по кварталам на шаге поиска не запрашивать.
Пустые метрики дальше означают отсутствие доступных данных; не искать замену UUID
и не считать HR-профиль доказательством наличия исторических метрик.
Сохрани подтверждённого человека для всех кварталов и отдельного продолжения по Agile.
