# Расчёт метрик вовлечённости по готовому составу структур

## Когда использовать

- Состав структур уже собран скиллом `get-managers-unit-id-array` (пакет получен) — этот
  скилл только рассчитывает метрики по готовому фильтру.
- Пользователь спрашивает метрики вовлечённости по известным структурам: индекс
  вовлечённости, конкретную метрику по названию («покажи метрики про нагрузку»),
  группы метрик.
- Нужен совокупный показатель по набору структур (`single`) или сравнение каждой
  структуры по отдельности (`circle`).
- **НЕ используй**, если структуры ещё не собраны: сначала скилл
  `get-managers-unit-id-array`, этот скилл сам состав НЕ ищет (см. «Если пакета нет»).

Скилл рассчитывает метрики вовлечённости по составу структур, собранному скиллом
`get-managers-unit-id-array`. Значения метрик доступны ТОЛЬКО через параметрические
метрики (поле `param_metrics`):

1. `index_map` — все индексы/метрики по волне → словарь `index_id → процент` (0..1, уже посчитан);
2. `index_value` — значение одного индекса по волне → `index_id → процент` (нужен `index_id`);
3. `metric_group_map` — все группы метрик по волне → словарь `group_id → процент` (0..1);
4. `metric_group_value` — значение одной группы по волне → `group_id → процент` (нужен `metric_group_id`).

Все четыре требуют `assignment_id` (UUID волны); `index_value` дополнительно `index_id`,
`metric_group_value` — `metric_group_id`.

Пустой Map `{}` или значение `0` у нужного `index_id`/`group_id` = данных нет — не выводи.

## Вход от скилла get-managers-unit-id-array — контракт пакета

Прежде чем считать, убедись, что у тебя есть пакет строго фиксированной формы от
предыдущего скилла. Принимай его как есть, не пересобирай форму массива.

1. **индикатор** (имя параметрической колонки в `involvement_metric`) — одно из:
   `agile_sub_tree_include_indicator` / `oshs_sub_tree_include_indicator` /
   `fos_sub_tree_include_indicator` / `fg_sub_tree_include_indicator`.
2. **массив ID** — имя поля и форма элемента зависят от индикатора; от режима зависит только
   СОСТАВ/число запросов, а форма каждого массива — нет (см. п.4):
   - `agile` / `fos` / `fg` → поле `unit_id_array`, элемент = число `ID`;
   - `oshs` → поле `company_unit_id_array`, элемент = пара `[company_name, ID]`.
3. **company_name** (только для `oshs`) — по умолчанию `"paosberbank"`.
4. **режим** — `single` или `circle`. Форма массива ID от режима НЕ зависит — массив всегда плоский:
   - `single` — весь массив одним плоским списком `[ID_1, ID_2, ...]`;
   - `circle` — N запросов, каждый с ОДНИМ элементом плоского массива: `unit_id_array: [ID_i]`
     (для oshs — `company_unit_id_array: [["paosberbank", ID_i]]`), результаты сравниваются.
     Вложенных форм `[[ID_1], [ID_2], ...]` НЕ существует.

Примеры пакета:

**agile, режим `single`** (2 структуры, одним запросом):
```json
{"индикатор": "agile_sub_tree_include_indicator", "режим": "single", "unit_id_array": [63858151, 64147725]}
```

**agile, режим `circle`** (N запросов, каждый с одним ID):
```json
Запрос 1: {"индикатор": "agile_sub_tree_include_indicator", "режим": "circle", "unit_id_array": [63858151]}
Запрос 2: {"индикатор": "agile_sub_tree_include_indicator", "режим": "circle", "unit_id_array": [64147725]}
```

**oshs, режим `single`** (2 структуры, одним запросом):
```json
{"индикатор": "oshs_sub_tree_include_indicator", "режим": "single", "company_name": "paosberbank", "company_unit_id_array": [["paosberbank", 10360345], ["paosberbank", 10320279]]}
```

**oshs, режим `circle`** (N запросов, каждый с одной парой):
```json
Запрос 1: {"индикатор": "oshs_sub_tree_include_indicator", "режим": "circle", "company_name": "paosberbank", "company_unit_id_array": [["paosberbank", 10360345]]}
Запрос 2: {"индикатор": "oshs_sub_tree_include_indicator", "режим": "circle", "company_name": "paosberbank", "company_unit_id_array": [["paosberbank", 10320279]]}
```

Для `fos` / `fg` пакет как у `agile` (поле `unit_id_array`, элемент = число `ID`), меняется `индикатор`.

**Если пакета нет** (структуры не собраны) — НЕ ищи структуры здесь сам. Собери состав
по инструкциям скилла `get-managers-unit-id-array`: если ты его `SKILL.md` уже читал в этом
чате — выполняй его шаги прямо из контекста (перечитывать файл НЕ нужно), иначе прочти его
одним `read_file`. Текущий скилл считает метрики только по готовому фильтру.
Если состав по инструкции собран, но массив всё ещё пуст — значит, человек не руководит
структурами; это штатно покрыто в первом скилле (раздел «ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА»).

## Источники данных

Текущий `assignment_id` (последняя волна, компания `paosberbank`) = `b870ba92-a8f1-42ba-a305-ee75726adccc`.
Справочники маппинга названий:
- `dm_core.involvement_index_metrics_dict` — `index_id` метрики → `title`;
- `dm_core.involvement_groups_dict` — `group_id` групповых метрик → `title`;

## Используемые инструменты

- `mcp_query` (сессия `heimdall`) — запросы к витринам вовлечённости.

## Режимы расчёта по массиву структур

Параметр `assignment_id` = `b870ba92-a8f1-42ba-a305-ee75726adccc` — используй только его.
`company_name` по умолчанию `"paosberbank"`. Если увидишь `"company_name": "ПАО Сбербанк"`
замени на `"company_name":"paosberbank"` — только так работает модель `involvement_metric`.

### Режим `single` (весь массив одним плоским списком)

Весь массив ID кладётся в `args` индикатора одним запросом — метрика агрегируется по всем
людям всех структур сразу. Используй по умолчанию (быстрее, меньше вызовов). Подходит, когда
нужен совокупный показатель по набору структур.

Форма массива для agile/fos/fg: `unit_id_array: [ID_1, ID_2, ...]` — **плоский список чисел**.
Если передать элемент как массив (`[[ID_1],[ID_2],...]`) — сервер вернёт
`parameter-type-invalid: параметр 'unit_id_array' ждёт Array(UInt64), элемент #0=[ID] не подходит`.

### Режим `circle` (по одной структуре на запрос)

По каждой структуре — отдельный запрос `involvement_metric` со своим ID в `args`, затем
результаты сравниваются между собой. Используй, когда пользователь явно хочет сравнение
каждой структуры по отдельности, либо когда режимом `single` метрика вернула пусто/мало.

Форма массива в каждом запросе ТА ЖЕ плоская, только с одним элементом:
- agile/fos/fg: запрос №i — `"args": {"unit_id_array": [ID_i]}` (НЕ `[[ID_i]]`);
- oshs: запрос №i — `"args": {"company_unit_id_array": [["paosberbank", ID_i]]}` (НЕ `[[["paosberbank", ID_i]]]`).

### Динамика между волнами — НЕ поддерживается (сразу отказ)

Вопросы про **изменение вовлечённости во времени** — «выросла/упала», «динамика»,
«по сравнению с прошлой/предыдущей волной», «где выросло сильнее всего с прошлой волны»,
«прирост», «падение вовлечённости с прошлой волны» — **невозможно** посчитать этим скиллом:

- `assignment_id` жёстко один (`b870ba92-…`, см. «Режимы расчёта») — это **актуальная** волна;
  «ЗАПРЕТ НА ПОДМЕНУ ВОЛНЫ» запрещает подставлять другие `assignment_id`;
- `index_values`/`metric_group_values` хранят «сырой» числитель/знаменатель по волнам,
  но **не итоговый процент** и **не за прошлую волну для сравнения** — помечены «не использовать»;
- дельта между волнами требует двух отдельных расчётов по двум `assignment_id`, а доступна только одна.

**На такой вопрос НЕ запускай расчёт и НЕ перебирай структуры** (это даёт десятки/сотни
`mcp_query` без результата). Сразу ответь одной фразой:

```
Динамика вовлечённости между волнами сейчас не поддерживается — доступен расчёт только по актуальной волне опроса Пульс. Задайте вопрос по текущей волне (индекс, метрики, сравнение структур), и я посчитаю.
```

Это касается в т.ч. вопросов вида «в каких командах выросло/упало сильнее всего» —
не пытайся эмулировать динамику перебором структур по текущей волне: ответ «где выросло»
из одной волны получить нельзя.

## СХЕМА `involvement_metric` и справочников (разрешено / не существует)

В модели `involvement_metric` всего 7 колонок и 4 параметрические метрики — держи в голове
весь список, здесь нечего «искать»:

| Колонка | Тип | Что это |
|---|---|---|
| `agile_sub_tree_include_indicator` | `UInt8` (**параметрическая**) | флаг «входит в agile-поддерево»; параметр `unit_id_array` |
| `oshs_sub_tree_include_indicator` | `UInt8` (**параметрическая**) | то же по линейной; параметр `company_unit_id_array` = `[[company, unit_id], …]` |
| `fos_sub_tree_include_indicator` | `UInt8` (**параметрическая**) | то же по ФОС; параметр `unit_id_array` |
| `fg_sub_tree_include_indicator` | `UInt8` (**параметрическая**) | то же по ФГ; параметр `unit_id_array` |
| `company` | `String` | код компании (на латинице, `paosberbank`) |
| `index_values` | `Map(UUID, Map(UUID, Array(UInt16)))` | «сырой» map числитель/знаменатель по волнам — **не использовать** |
| `metric_group_values` | `Map(UUID, Map(UUID, Array(UInt16)))` | то же по группам — **не использовать** |

| Метрика (только в `param_metrics`) | Параметры |
|---|---|
| `index_map` | `assignment_id` |
| `index_value` | `assignment_id`, `index_id` |
| `metric_group_map` | `assignment_id` |
| `metric_group_value` | `assignment_id`, `metric_group_id` |

**Колонки, которых НЕТ — не пиши их ни в каком запросе:**

| Не существует | Как правильно | Последствие ошибки |
|---|---|---|
| `index_map` / `metric_group_map` / `index_value` / `metric_group_value` в `columns` | только в `param_metrics: [{"name": ..., "args": {...}}]` | `unknown-column` («параметрическая метрика, вызови её в param_metrics») |
| `indicator` / `unit_id_array` / `company_unit_id_array` как колонка | только в `filters.type="condition_param"` → `name` + `args` | `unknown-column` |
| `assignment_id`, `wave`, `index_id` как колонка | `assignment_id` — только аргумент метрики; `index_id`/`metric_group_id` — только аргументы `*_value` | `unknown-column` |
| `title`/`name` метрики как колонка | метрики агрегируются, названия раскладываются из справочников после ответа | `unknown-column` |
| `fact_count` | в `involvement_metric` метрики численности нет | `unknown-metric` |
| `segment` / `segment_name` / `segment_include_indicator` | в `involvement_metric` НЕТ (сегмент есть только в `employee_actual`) | `unknown-column` |
| `agile.unit_id_tree` / `oshs.unit_id_tree` | в `org_structure` колонки БЕЗ префикса: `unit_id_tree` | `unknown-column: maybe you meant 'unit_id_tree'` |
| `unit_id_array` / `company_unit_id_array` в `param_metrics.args` | только в `filters.type="condition_param".args` | `unknown-parameter` |

Справочники (обе — обычные модели, без параметров):

| Модель | Колонки |
|---|---|
| `dm_core.involvement_index_metrics_dict` | `id` (UUID), `type` (`индекс`/`метрика`), `title`, `description` |
| `dm_core.involvement_groups_dict` | `id` (UUID), `title`, `description` |

- фильтровать справочник по названию — `{"type":"condition_like","column":"title","operator":"ILIKE","pattern":"%вовлеч%"}` (шаблон в `pattern`);
- у `involvement_groups_dict` колонки `type` НЕТ — запрос с ней падает (`unknown-column`);
- `id` в справочнике строго UUID — сравнивать/подставлять нужно ровно тот ключ, что пришёл из
  `index_map`/`metric_group_map`. На стендах справочники могут отдавать пустые строки — это
  ограничение витрины, а не повод изобретать `title`;

**Если `index_map`/`metric_group_map` вернули `{}`** — данных по волне для этой структуры
нет; так же отвечает запрос с несуществующим `assignment_id`. Значит, дело в волне или
в составе, но НЕ в `assignment_id` — подставлять другой `assignment_id` из других таблиц
запрещено (**см. Запреты**).

## Пагинация: общее правило для ВСЕХ запросов

Каждый ответ `mcp_query` содержит `limit`, `offset` и `has_next_page`. Правило
действует для ЛЮБОГО запроса этого скилла (Exp-5, Exp-6, справочники) —
независимо от того, написано ли оно рядом с конкретным примером, и для запросов
скилла сбора `get-managers-unit-id-array`:

**Если `has_next_page: true` — продолжай сбор с `offset`.**
Увеличивай `offset` на использованный `limit` (остальные параметры те же) и повторяй
запрос, пока не получишь `has_next_page: false`. Не останавливайся на середине
выборки и не считай данные собранными, пока страница не последняя.

Запрос следующей страницы (вырос только `offset`) — это НЕ повтор из
«Запрет на зацикливание»: тот запрет — про вызовы с полностью идентичными параметрами.
То же правило относится к режиму `circle`: каждая интересующая структура считается
со своим `limit`/`offset`, пока её страница не последняя.

## ПРИМЕРЫ ГОТОВЫХ ЗАПРОСОВ

### Exp-5. mcp_query: метрики вовлечённости по структуре (`condition_param`-фильтр + `param_metrics`)

Фильтр ставится по структуре. Значения читай параметрической метрикой `index_map`
(или `metric_group_map` для групп). `columns` может быть пустым. Не клади параметрические
колонки/метрики в `columns`.

⚠️ **ВАЖНО:** `unit_id_array` передаётся ТОЛЬКО в `filters.args`, НЕ в `param_metrics.args`
(у `index_map`/`metric_group_map` в `args` — только `assignment_id`; иначе `unknown-parameter`).

Для agile-структуры (`index_map` + `metric_group_map`, режим `single` с массивом ID):
```json
{
  "schema": "dm_core",
  "logic_model": "involvement_metric",
  "columns": [],
  "param_metrics": [
    {"name": "index_map", "args": {"assignment_id": "b870ba92-a8f1-42ba-a305-ee75726adccc"}},
    {"name": "metric_group_map", "args": {"assignment_id": "b870ba92-a8f1-42ba-a305-ee75726adccc"}}
  ],
  "filters": {
    "type": "condition_param",
    "name": "agile_sub_tree_include_indicator",
    "operator": "=",
    "value": 1,
    "args": {"unit_id_array": [63858151, 64147725]}
  },
  "limit": 1,
  "offset": 0
}
```

Для oshs-структуры (линейная) — индикатор другой, параметр парой `[company_name, unit_id]`,
режим `single` (несколько пар одним списком), те же `index_map`/`metric_group_map`:
```json
{
  "schema": "dm_core",
  "logic_model": "involvement_metric",
  "columns": [],
  "param_metrics": [
    {"name": "index_map", "args": {"assignment_id": "b870ba92-a8f1-42ba-a305-ee75726adccc"}},
    {"name": "metric_group_map", "args": {"assignment_id": "b870ba92-a8f1-42ba-a305-ee75726adccc"}}
  ],
  "filters": {
    "type": "condition_param",
    "name": "oshs_sub_tree_include_indicator",
    "operator": "=",
    "value": 1,
    "args": {"company_unit_id_array": [["paosberbank", 10360345], ["paosberbank", 10320279]]}
  },
  "limit": 1,
  "offset": 0
}
```

Маппинг тип → индикатор (берётся из пакета скилла сбора):
- `agile` → `agile_sub_tree_include_indicator`, `args.unit_id_array: [ID, ...]`;
- `oshs` → `oshs_sub_tree_include_indicator`, `args.company_unit_id_array: [[company_name, ID], ...]`;
- `fos` → `fos_sub_tree_include_indicator`, `args.unit_id_array: [ID, ...]`;
- `fg` → `fg_sub_tree_include_indicator`, `args.unit_id_array: [ID, ...]`.

Результат:
- `index_map` = словарь `index_id → процент` (0..1);
- `metric_group_map` = словарь `group_id → процент` (0..1);
- процент уже посчитан внутри метрики, пересчитывать НЕ нужно (умножь на 100 для %).

В режиме `single` все ID идут в одном `args` одним плоским массивом (один запрос). В режиме `circle` —
по одному запросу на каждый ID (`unit_id_array: [ID_i]`, форма та же плоская), результаты собираешь в таблицу сравнения.

## Разложение метрик

Вызови Exp-5 с выбранным уровнем и параметрической метрикой `index_map` (или `metric_group_map`).
Боевая волна задаётся `assignment_id` = `b870ba92-a8f1-42ba-a305-ee75726adccc`, используй только её.

- ключи `index_map` (`index_id`) → название бери из `dm_core.involvement_index_metrics_dict` (Exp-6);
- ключи `metric_group_map` (`group_id`) → название из `dm_core.involvement_groups_dict` (Exp-6);
- «Индекс вовлеченности» (общий) = `index_id` `6b4d7a91-4671-438a-8b97-de0ed285121f`;
- значение — уже готовый процент (0..1), умножь на 100 для вывода; пустая Map `{}` или
  отсутствующий ключ = данных нет.

**Несколько `index_value` в одном запросе:** сервер возвращает колонки `index_value_1`,
`index_value_2`, … в порядке перечисления в `param_metrics`. Соотноси их по порядку `args`,
выводи пользователю названия из справочника, технические имена `index_value_N` в ответе
НЕ показывай.

Приведи результаты в табличном виде.
К метрикам применяй правило: если метрика вернула пустой объект `{}` или значение `0` — не выводи её.

Если пользователь просит одну конкретную метрику по названию — найди её `id`: сверь `title`
в `dm_core.involvement_index_metrics_dict` (для `index_id`) или `dm_core.involvement_groups_dict`
(для `group_id`). Затем вместо `index_map`/`metric_group_map` передай в Exp-5 параметрическую
метрику `index_value` (с `args: {"index_id": "<id>"}`) или `metric_group_value`
(с `args: {"metric_group_id": "<id>"}`). `assignment_id` — тот же, что на шаге выше.
Не нашёл названия в справочнике — сообщи об этом, не подставляй похожее.

### Как замапить index_map и metric_group_map

Параметрические метрики возвращают UUID-ключи, а не названия. Порядок:

1. `index_map` → ключи это `index_id`. Название каждого бери из `dm_core.involvement_index_metrics_dict`
   (Exp-6): подставь ключ в колонку `id`, получишь `title`;
2. `metric_group_map` → ключи это `group_id`. Название бери из `dm_core.involvement_groups_dict`
   (Exp-6): ключ → колонку `id`, получишь `title`;
3. Один и тот же `index_id` встречается в обеих метриках — но в `index_map` это отдельный показатель,
   в `metric_group_map` — его вклад внутри группы. Показывай пользователю с названием из нужного
   справочника, UUID в ответе НЕ выводи.

### Саджест метрик (suggestion)

После вывода результатов добавь:

> 💡 **Ещё метрики опроса доступны** (категории: доверие, руководитель, нагрузка,
> признание, условия). Назовите тему — покажу топ-5 по категории.

**Пользователь назвал тему/категорию («покажи метрики про нагрузку»):** ОДИН запрос `index_map`
(он уже возвращает все метрики волны) → по справочнику `involvement_index_metrics_dict` отфильтруй
ключи, чьи `title` подходят теме → выведи топ-5 по значению. НЕ делай N вызовов `index_value` по
каждой метрике — это лишние запросы и алиасы `index_value_N`. После ответа с саджестом ставь
Новый вопрос пользователя перерутится с контекстом диалога.

**НЕЛЬЗЯ показывать пользователю внутренности запроса.** Никакие UUID (`index_id`, `group_id`,
`person_id`), технические заголовки из справочника (`involvement_index_metrics_dict`), имена
параметрических колонок (`index_map`, `agile_sub_tree_include_indicator`) и `unit_id`
в ответе НЕ выводи. В ответе — только читаемые названия метрик и проценты. Если в названии метрики
или заголовке таблицы затесался идентификатор/техническое имя — замени на человекочитаемое или
убери вовсе. Служебные сводные индексы («Индекс вовлеченности (общий)», «Уровень доверия между
командами (индекс)») выводи только в шапке/сводке ключевых индексов, НЕ в списках значений
метрик — иначе это выглядит как «технические части».

Не выгружай справочник целиком и не делай по строке на каждый `id`: справочник маленький,
бери разом с запасом по `limit` (в примерах Exp-6 — 50) и раскладывай `title` по `id` уже в
ответе. `id` из `index_map`/`metric_group_map` подставляй ровно в том виде, в каком он пришёл —
иначе строка «не найдётся», и ты выведешь неверное название.

Пример: `index_map` вернул `{"6b4d7a91-4671-438a-8b97-de0ed285121f": 0.62}` →
по `involvement_index_metrics_dict` это «Индекс вовлеченности» → выводи «Индекс вовлеченности 62%».
