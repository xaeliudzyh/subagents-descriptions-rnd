# Поиск и подбор кандидатов под ротацию (search-rotating-top600)

Скилл вызывается, когда пользователь хочет **найти кандидатов на место позиции или персоны под ротацию**. Является самостоятельным.

## Входные данные

От пользователя ожидается **позиция** (название или id) и/или **персона** (ФИО и/или ТН и/или person_id) под ротацию, на которых подбирать кандидатов.

## Алгоритм работы

1. Определяем ТН персоны под ротацию и/или id позиции тулом `resolve_top600_employee`:
   - персона под ротацию — `employee_id`, `person_id` (id профиля) или `full_name`; позиция — `position_id`;
   - ТН самого пользователя (запрашивающего руководителя) **не определяем**: тулы ротации получают его от сервиса;
   - если пользователь называет ротируемым **себя** («на моё место», «на мою позицию») — ротация на собственное место не выполняется: переходим на скилл `search-successor-top600`. Далее инструкция по этому скиллу не исполнятется - только то, что написано в `search-successor-top600`;
   - вернулся `matches` — уточняем у пользователя, кого он имел в виду;
   - вернулось `message` без `matches` при поиске по уменьшительному / разговорному имени («Аня», «Саша») — один раз повторяем вызов с полным именем («Анна», «Александр» / «Александра»), фамилию оставляем как есть;
   - вернулось `message` без `matches` (в том числе после повтора с полным именем) — персоны нет среди сотрудников ТОП-600, завершаем работу по скиллу.
2. Вызываем тул `get_rotation_candidates` для определения списка кандидатов:
   - `potential_rotatable_employee_id` — ТН персоны под ротацию из шага 1 и/или `potential_rotatable_position_id` — id позиции (одно из двух обязательно);
   - ТН запрашивающего не передаём — его подставляет сервис.
3. Разбираем результат работы тула — может вернуться два варианта:
   - вернулся отказ о том, что сотрудник или позиция **не в подчинении** текущего пользователя — трек «Ротации» продолжить нельзя:
     - дальнейшие шаги этого скилла не выполняем, тулы ротаций больше не вызываем и подбор с другими аргументами не повторяем;
     - сообщаем пользователю, что подбор под ротацию недоступен, и предлагаем подобрать преемников на это место:
       > «Подобрать кандидатов под ротацию на место <ФИО / позиция> нельзя — сотрудник не в вашем подчинении. Могу подобрать преемников на это место. Подобрать?»
     - сами на трек «Преемники» **не переходим**: ждём ответа пользователя;
     - пользователь согласился — выполняем скилл `search-successor-top600` для этого сотрудника (позиции): ТН уже определён на шаге 1, повторно не спрашиваем; отказался — завершаем работу;
   - если вернулись целевые кандидаты — оцениваем их по логике, описанной в `candidate-list-common-successor-rotating-top600`.
4. Формируем детальную оценку соответствия по структуре и методологии, описанной в скилле `candidate-analyze-successor-rotating-top600`.
5. Формируем и возвращаем результат пользователю. **ОБЯЗАТЕЛЬНО сохрани заданную структуру ответа (не добавляй новых блоков и не убирай имеющиеся):**
   1. Информация о позиции: одной строкой строго в формате «Позиция: <название должности>»
      (название — первая строка `position_text`; грейд и id позиции не выводим, имена полей тоже).
      Пример: «Позиция: Директор ДИТ». Слово «ротация» в тексте пользователю не используем.
   2. Текущие преемники на позиции (на основе поля `successors`): ФИО через запятую — они должны быть **кликабельными** `[full_name](https://hr.sberbank.ru/platform/profile/<person_id>)`.
   3. Список кандидатов (от лучшего балла к худшему). Колонки списка (формируем на основании `candidates`):
      - **"ФИО"** — `employee_full_name` в виде ссылки на профиль: `[employee_full_name](https://hr.sberbank.ru/platform/profile/<person_id>)`;
      - **"Название должности"** — `professionlevel_name`;
      - **"Название подразделения"** — последнее название в строке `unit_names`;
      - **"Оценка соответствия"** — финальный балл `score` из ответа `score_rotation_candidates` (шаг 3), по нему ранжируется список.
        Сырой `ml_score` пользователю не показываем;
      - **"Рекомендован по стажу в роли"** — «да» / «нет» по `with_rotate_status`.
   4. Детальная оценка соответствия по структуре и методологии, описанной в скилле `candidate-analyze-successor-rotating-top600` (прочитан на шаге 3.1).
6. Сохраняем информацию по предложенным кандидатам через тул `saved_rotatable`, куда передаём структурированный анализ соответствия по каждому кандидату:
   - `oshs_position_id` — ID позиции, в пул которой сохраняем: скалярный `position.oshs_position_id` **из ответа `get_rotation_candidates`**;
   - `chat_id` — передавать не нужно: сервис подставит ID текущего диалога сам;
   - `candidates_info` — лист словарей по каждому кандидату: `person_id`, `final_score` (финальный балл `score` из шага 3), `text_score_explanation`, `text_strengths`, `text_risk_zone`.
   Сохраняем полученные `talent_pool_id` (и `talent_pool_url`) — они понадобятся для шага добавления кандидатов и ссылки на пул.
7. Предлагаем пользователю добавить на позицию предложенных кандидатов, указав тех из текущего списка, кого хочет добавить:
   > «Добавить кого-либо из кандидатов на рассмотрение? Укажите, кого хотели бы добавить»
8. Если пользователь решил добавить кандидатов — добавляем по методологии, описанной в скилле `add-to-rotating-list-top600`.

## Ссылки на смежные скиллы

- `resolve_top600_employee` — тул определения ТН персоны по ТН, person_id(id профиля), ФИО или id позиции.
- `candidate-list-common-successor-rotating-top600` — методика подсчёта финального балла.
- `candidate-analyze-successor-rotating-top600` — логика формирования анализа по кандидатам.
- `search-successor-top600` — предлагается, если сотрудник (позиция) не в подчинении пользователя; переход только после его согласия.
- `list-rotatable-subordinates-top600` — список сотрудников команды под ротацию, из которого может прийти выбранный сотрудник.
