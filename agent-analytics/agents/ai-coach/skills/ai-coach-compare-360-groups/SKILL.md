# Инструкция для агента: сравнение результатов 360 с группой ТОП-600

## Когда использовать

Скилл применяется, когда человек просит сравнить свою оценку 360 с оценочной
группой ТОП-600:

- «как я выгляжу на фоне коллег по функциональному блоку»;
- «сравни меня с моим функциональным блоком»;
- «мой бенчмарк по оценке 360»;
- «какой средний балл по блоку», «средний по блоку», «как у коллег в блоке» —
  этот же скилл.

Единственный доступный разрез сравнения — **функциональный блок**.

Если запрос про средний балл, а не про распространённость: баллы в этом скилле не
считаются. Скажи это одной фразой и покажи сравнение в доступном виде — долю коллег,
у которых компетенция попала в сильные стороны или зоны роста. Придумывать баллы
нельзя.

Скилл запускается **только по запросу пользователя** о сравнении с оценочной
группой. Сам коуч сравнение не инициирует: после показа результатов 360 основным
остаётся коучинговый вопрос 2.1, а сравнение предлагается отдельным запросом и
только по функциональному блоку.

Запрос на сравнение приоритетнее формы запроса A: если в запросе есть и слово
«360», и просьба сравнить с блоком, ответ строится по этому скиллу — то есть
только данные сравнения.

Если пользователь просит сравнение с другой когортой — по **тербанку**, по ТОП-600
целиком (по всему сегменту) или с любой другой группой — сообщи одной фразой, что
возможно сравнение только с собственным функциональным блоком, и предоставь его.

Сравнение по группам оценщиков (руководитель, коллеги, подчинённые, самооценка,
паутинка) — это другой скилл, `get_employee_web_summary`. Здесь оно не выполняется и
в ответ не добавляется.

## Что именно сравнивается

Сравниваются **не баллы**, а вхождение компетенции в списки сильных сторон и зон
роста:

> «У Вас сильная сторона «[компетенция]», как и у [доля]% сотрудников
> [разрез] ([размер среза] чел.)».

Такой расчёт строится на массивах `strong_points` и `growth_points` и не требует
баллов: один список названий на человека весит немного, поэтому группа собирается за
один запрос, без страниц и усреднений.

Не заменяй эту формулировку на «выше/ниже среднего»: баллы здесь не используются,
утверждение о превышении среднего балла из этих данных не выводится.

## Используемый инструмент

- **MCP-сессия:** `heimdall`
- **Инструмент:** `mcp_query`

Каждый шаг алгоритма — отдельный `mcp_query`. Когда нужно найти другого человека
по ФИО — используй `search_persons_by_fio` (см. Предварительные условия).

## Предварительные условия (prerequisite)

1. Получи результаты 360 сотрудника через heimdall-скилл `get_employee_web_summary`
   с его `person_id`: сильные стороны и зоны роста. Массивы `competence_names`,
   `competence_roles`, `competence_assessments` в этом скилле не используются.

   Если по `person_id` результатов нет — сообщи: «На текущий момент результатов теста
   360 у [Имя Отчество] нет» и заверши сравнение.

2. Для собственных результатов `person_id` берётся из сессии — искать его не
   нужно. Если сравнивают другого человека, а его `person_id` неизвестен — найди
   его по ФИО через инструмент `search_persons_by_fio` (он возвращает
   `personUuid` — это и есть `person_id`).
   В задании от пользователя сотрудник может быть назван
   по ФИО — работай с его `person_id`, а не с `person_id` пользователя: сравнение
   идёт для того человека, о котором спросили, и его же строка исключается из
   группового подсчёта.

3. Если по ФИО найдено несколько сотрудников — не выбирай наугад: покажи найденных
   (ФИО, должность) и спроси, о ком речь, одним вопросом. Если найден ровно один —
   работай с ним.

4. **Функциональный блок для текущего пользователя уже есть в
   контексте сессии** — не запрашивай его из `dm_core.employee_actual`. Запрос в
   витрину делается только для другого человека (шаг B).

## Алгоритм сравнения

### Шаг A. Сильные стороны и зоны роста сотрудника

Возьми из `get_employee_web_summary`: списки сильных сторон и зон роста. Если списки
пустые — сообщи, что сравнивать нечего, и заверши.

### Шаг B. Сведения о функциональном блоке сотрудника

**Для текущего пользователя — данные берутся из контекста сессии.** Сегмент и
функциональный блок уже есть в персональных данных сессии (`segment`, `fblock_name`).
Бери их оттуда и **не делай** запрос в `dm_core.employee_actual` для себя: это
лишний шаг и источник расхождений.

**Только если сравнивается другой человек (по ФИО/чужой `person_id`) — один
запрос в витрину** по его `person_id`:

```json
{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["person_id", "fblock_name", "segment"],
  "filters": {
    "type": "condition",
    "column": "person_id",
    "operator": "=",
    "value": "<person_id>"
  },
  "limit": 1
}
```

**Функциональный блок — это только поле `fblock_name`**.
Не бери его из `position_name` и других текстовых полей: в должности может стоять
название блока, которое не совпадает с `fblock_name`, и группа соберётся неверная.
Код блока (`fblock_code`) не подставляй, если он не получен из данных.

Если `fblock_name` пустой (NULL или пустой массив) — группу сравнения не строить и
сказать, что сравнение по блоку построить нельзя.

### Шаг C. Сбор списка `person_id` для группы сравнения

Собирается **только одна группа** — ТОП-600 того же функционального блока.
Другие разрезы не собираются.

Группа — сотрудники из ТОП-600 (`segment` = `'top600'`). Не убирай условие
`segment`: без него в группу попадут все сотрудники блока.

```json
{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["person_id"],
  "filters": {
    "type": "and",
    "conditions": [
      {"type": "condition", "column": "segment", "operator": "=", "value": "top600"},
      {"type": "condition", "column": "fblock_name", "operator": "=", "value": "<fblock_name сотрудника>"}
    ]
  },
  "limit": 1000,
  "order_by": [{"field": "person_id", "kind": "column", "direction": "asc"}]
}
```

Ограничение объёма: `limit` ужимается до серверной границы (1000), большие выборки
листаются через `offset`. Для одного блока обычно хватает одного вызова.

### Шаг D. Списки сильных сторон и зон роста по группе

Запрос к `dm_special.assessment_360_feedback` по списку `person_id`, только два
массива:

```json
{
  "schema": "dm_special",
  "logic_model": "assessment_360_feedback",
  "columns": ["person_id", "strong_points", "growth_points"],
  "filters": {
    "type": "condition_in",
    "column": "person_id",
    "operator": "IN",
    "value": ["<uuid_1>", "<uuid_2>", "..."]
  },
  "limit": 1000
}
```

Запрос выполняется один раз для группы блока. Если список `person_id` очень
длинный, разбивай его на порции примерно по сто штук и объединяй ответы.

**Один и тот же запрос для любой формулировки вопроса.** Не меняй набор колонок
и фильтры в зависимости от того, как спросили: если просят «средний по блоку»
или «как у коллег», запрос тот же самый. Разница только в оформлении ответа.

Строки, где `strong_points` и `growth_points` оба пустые (NULL или пустой
массив), в знаменатель **не попадают** — см. шаг E.

### Шаг E. Подсчёт долей

Порядок шагов фиксирован и одинаков в любом диалоге — от него зависит число
в ответе:

1. Исключи из выборки строку самого сотрудника — сравнение идёт с коллегами.
2. **Отбери в знаменатель только те строки группы, у которых есть заполненные
   списки:** хотя бы один непустой `strong_points` или `growth_points`. Строки,
   где оба списка пустые/NULL, отбрасываются целиком и **не считаются как «нет
   компетенции»**. Это касается любого запроса — «средний по блоку», «как у
   коллег», «насколько распространена компетенция».
3. Нормализуй названия (обрежь пробелы, сравни без учёта регистра), иначе
   одинаковые компетенции не совпадут.
4. По каждой компетенции из списков сотрудника посчитай, у скольких
   сотрудников группы она есть в `strong_points` и у скольких — в
   `growth_points`. **Считай оба числа всегда**, даже если в ответ пойдёт
   только одно.
5. **Знаменатель одинаков для всех компетенций** — это число строк из шага 2.
   Не считай долю отдельно по каждой компетенции с разным знаменателем и не
   подменяй его общим числом людей в группе (например, 12), если результаты
   заполнены только у части (например, 8).
6. **Бери долю только из того списка, где компетенция у самого сотрудника.**
   - Компетенция в его `strong_points` → показываешь долю коллег с ней в
     `strong_points`.
   - Компетенция в его `growth_points` → показываешь долю коллег с ней в
     `growth_points`.

   **Запрет:** подставлять долю из `growth_points` к сильной стороне сотрудника
   и наоборот. Пример ошибки: у сотрудника «Доверие» в зонах роста, у 75%
   коллег оно в сильных сторонах — писать «13% коллег», потому что 13% — это
   доля зон роста, нельзя.
7. Доля = число совпадений / знаменатель, округли до целого процента.
8. Если совпадений нет ни у кого — так и напиши («ни у кого в группе этой
   компетенции в сильных сторонах нет»), придумывать процент нельзя.
9. Если знаменатель равен нулю (результатов 360 в блоке нет ни у кого) —
   сравнение не строится; скажи это без процентов.

### Число только из пересчёта (КРИТИЧЕСКИ ВАЖНО)

Каждое число в ответе — результат прямого пересчёта по конкретной выборке этого
запроса. **Запрещено** оценивать процент «на глаз», округлять до красивого или
брать число из другого запроса/ответа.

Как считать (последовательность обязательна):

1. **Зафиксируй знаменатель — один раз.** Это число строк в ответе `mcp_query`
   после шага 2. Если в выборке есть `person_id` самого сотрудника — вычти его.
   Выпиши это число и дальше всюду используй только его. Не пересчитывай
   знаменатель заново для каждой компетенции и не меняй его между запросами.
2. **Посчитай числитель поимённо.** Пройди каждую строку выборки и отметь, у
   кого компетенция есть в нужном списке. Считай именно строки, а не
   «прикидывай»: число должно быть перечислимым (например: `bdd640fb`,
   `beb79919`, …).
3. **Посчитай процент арифметикой:** `числитель / знаменатель × 100`,
   округление до целого.
4. **Проверь обратным делением:** `числитель / знаменатель` должно совпадать с
   процентом (±1 на округлении). Если не совпадает — пересчитай, не отправляй.
5. **В ответе печатай оба числа рядом:** «у [доля]% коллег ([числитель] из
   [знаменатель])». Если числитель и знаменатель в скобках не дают указанный
   процент — это ошибка, ответ отправлять нельзя.

Частые сбои, которые запрещены:

- писать «7 из 9», когда в выборке таких 6 — числитель не пересчитан;
- брать 78% (доля «Доверия») для чужой компетенции — число из другой строки;
- считать от 8, а в скобках писать 9 — разные знаменатели в одном ответе;
- писать 56% там, где 6 из 9 = 67% — процент не получен делением.

### Самопроверка чисел перед отправкой

Перед тем как отправить ответ, сверь каждую строку:

- одно и то же число в скобках и в тексте: «67% (6 из 9)» — не «67% (7 из 9)» и
  не «78% (6 из 9)»;
- `числитель/знаменатель` действительно даёт указанный процент (проверяй делением);
- знаменатель одинаков во всех строках и равен числу коллег с заполненными
  результатами;
- ни одно число не взято из другого запроса или другой компетенции;
- если данные изменились (другая выборка) — числа пересчитаны заново, а не
  скопированы из прошлого ответа;
- компетенция у сотрудника в сильных сторонах → в ответе доля из сильных
  сторон группы;
- компетенция у сотрудника в зонах роста → в ответе доля из зон роста группы;
- все проценты делятся на один и тот же знаменатель — число коллег с
  заполненными результатами;
- в тексте нет долей, взятых из другого списка, и нет вывода «уникально для
  Вас», если в группе компетенция часто встречается в противоположном списке.

## Как оформить ответ

- обращайся на «Вы», к сотруднику — по имени и отчеству;
- **коротко и компактно**, без пространных объяснений и без таблиц на весь экран;
- **запрещена разметка-глифы** ✅ и ⚠️ и подобные значки в ответе: пиши словами
  («в сильных сторонах», «в зонах роста»);
- сначала 2–3 компетенции, которые чаще всего встречаются в сильных сторонах группы —
  это точки совпадения с коллегами;
- затем 1–2 зоны роста и их распространённость в группе;
- всегда указывай разрез, номер среза и знаменатель: «по функциональному блоку
  «[блок]», [N] чел. с заполненными списками». В N — именно знаменатель из шага E,
  а не число всех сотрудников блока.
- если когорта пустая или данных нет — коротко скажи, что сравнение по блоку
  построить нельзя;
- **один разрез — один ответ.** В ответе только функциональный блок;
- не раскрывай данные отдельных сотрудников: только доли, размер группы и названия
  компетенций.

Структура: одна строка о том, что сравнение по функциональному блоку, затем 2–3
компетенции с долями, затем 1–2 зоны роста.

### Ответ только про сравнение с группой

Ответ этого скилла — ровно про сравнение с функциональным блоком, и больше ничего:

- **только собственный функциональный блок:** если пользователь назвал другую
  когорту, одной фразой скажи, что возможно сравнение только с собственным блоком;
- **не добавляй** в конец разбивку по группам оценщиков (паутинку: руководитель,
  коллеги, подчинённые, самооценка), общие выводы по собственной оценке 360 и
  другие блоки отчёта `get_employee_web_summary`;
- разбивка по ролям оценщиков — это другой скилл (`get_employee_web_summary`),
  и она выводится только если пользователь **явно** её попросил отдельным
  запросом («покажи, как оценивали руководитель и коллеги», «паутинка»);
- если пользователь попросил именно сравнение («сравни меня с блоком») —
  достаточно только той части, где указаны разрез, размер среза и доли
  компетенций;
- **без коучингового вопроса в конце.** Заканчивай ответ после долей: ни вопрос
  2.1, ни любой другой коучинговый вопрос к ответу этого скилла не добавляется.

Если пользователь задал неподдерживаемую когорту (тербанк, сегмент целиком или
другая группа), ответ строится в два предложения: первой фразой — что возможно
сравнение только с собственным функциональным блоком, дальше — само сравнение по
блоку с сокращённой строкой-шапкой. Длинное объяснение про то, какие когорты
недоступны и как считаются доли, в такой ответ не добавляй.

Пример формы для неподдерживаемой когорты:

> Сравнение возможно только с Вашим функциональным блоком «[блок]». По блоку
> «[блок]» ([N] коллег с заполненными результатами 360): …

## Пример формы ответа

> По функциональному блоку «[блок]» ([N] коллег с результатами 360):
> «[компетенция]» есть в сильных сторонах у [доля]% коллег ([числитель] из [N]) —
> у Вас тоже.
> «[компетенция]» — [доля]% коллег ([числитель] из [N]) тоже отмечают её в зонах
> роста, у Вас так же.

Второй пример — компетенция у коллег чаще в сильных сторонах, а у сотрудника в зонах
роста (доля берётся из `growth_points`!):

> «Доверие» — Вы отметили его в зонах роста; [доля]% коллег ([числитель] из [N])
> тоже в зонах роста. У остальных коллег этого среза оно в сильных сторонах —
> это заметное отличие от группы.

Проверка примера: если числитель 2, а знаменатель 9, то в тексте должно быть
«22% (2 из 9)», а не «11%» и не «2 из 8».
