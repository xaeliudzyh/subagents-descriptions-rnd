## С ЧЕГО НАЧАТЬ

Вопрос про «мою команду / мои команды / под моим руководством» → **первый вызов — всегда
`mcp_query` к `dm_core.employee_actual`** (шаг 1.3 ниже), с `person_id` из служебного блока
системного промпта. Не вызывай `search_persons_by_fio`, не спрашивай ФИО, не ищи структуру
по названию — данные пользователя уже в профиле.

`get_structure_names_tool` / `search_persons_by_fio` нужны только когда пользователь
**сам назвал** название структуры или другое ФИО.

**Сегмент топ-600 — проверяется ВСЕГДА, включая «мою команду»:** если пользователь назвал
ФИО, `person_id`, должность, явно упомянул «топ-600 / TOP-600 / ТОП-600» **или спрашивает про
«мою команду»** — после определения `person_id` (шаг 1.1) **всегда** проверь по
`employee_actual`, относится ли этот человек к сегменту (`segment = 'top600'` и
`is_director = 1`):
- **свой `person_id` из служебного блока** — проверяй сегмент **параллельно с шагом 1.3**
  (тем же `person_id`), т.к. сам пользователь тоже может быть топ-600 руководителем;
- **чужой `person_id`** (пользователь назвал ФИО/должность) — проверяй сегмент до выбора
  маршрута, как и раньше.

Если человек из топ-600 — НЕ иди обычным маршрутом «команды руководителя», а переходи сразу
в раздел «Разрез по сегменту (топ-600)». Признак «топ-600» может стоять прямо в вопросе либо
следовать из ФИО/должности человека — проверяй сегмент по `person_id` во всех случаях.

## Результат скилла — контракт пакета для get-involvement-metrics-by-unit-id

По итогу у тебя на руках пакет со строго фиксированными полями. Передавай его во второй
скилл **как есть**, не пересобирай форму массива на стороне расчёта.

Пакет:

1. **индикатор** (имя параметрической колонки в `involvement_metric`) — сразу одно из:
   - `agile_sub_tree_include_indicator`
   - `oshs_sub_tree_include_indicator`
   - `fos_sub_tree_include_indicator`
   - `fg_sub_tree_include_indicator`
2. **массив ID** — имя поля и форма элемента зависят от индикатора; от режима зависит только
   СОСТАВ/число запросов, а форма каждого массива — нет (см. п.4):
   - `agile` / `fos` / `fg` → поле `unit_id_array`, элемент = число `ID`;
   - `oshs` → поле `company_unit_id_array`, элемент = пара `[company_name, ID]`.
3. **company_name** (только для `oshs`) — по умолчанию `"paosberbank"`.
4. **режим** — `single` или `circle`. Форма массива ID от режима НЕ зависит — массив всегда плоский:
   - `single` — весь массив одним плоским списком, метрика считается сразу по всем структурам:
     `[ID_1, ID_2, ...]`;
   - `circle` — N запросов, каждый с ОДНИМ элементом плоского массива: `unit_id_array: [ID_i]`
     (для oshs — `company_unit_id_array: [["paosberbank", ID_i]]`), результаты сравниваются.
     Вложенных форм `[[ID_1], [ID_2], ...]` НЕ существует — они дают `parameter-type-invalid`.

### Примеры пакета

**agile, режим `single`** (2 структуры, одним запросом):
```json
{
  "индикатор": "agile_sub_tree_include_indicator",
  "режим": "single",
  "unit_id_array": [63858151, 64147725]
}
```

**agile, режим `circle`** (те же 2 структуры: N запросов, каждый с одним ID):
```json
Запрос 1: {"индикатор": "agile_sub_tree_include_indicator", "режим": "circle", "unit_id_array": [63858151]}
Запрос 2: {"индикатор": "agile_sub_tree_include_indicator", "режим": "circle", "unit_id_array": [64147725]}
```

**oshs, режим `single`** (2 структуры, одним запросом; элемент — пара `[company_name, ID]`):
```json
{
  "индикатор": "oshs_sub_tree_include_indicator",
  "режим": "single",
  "company_name": "paosberbank",
  "company_unit_id_array": [["paosberbank", 10360345], ["paosberbank", 10320279]]
}
```

**oshs, режим `circle`** (те же 2 структуры: N запросов, каждый с одной парой):
```json
Запрос 1: {"индикатор": "oshs_sub_tree_include_indicator", "режим": "circle", "company_name": "paosberbank", "company_unit_id_array": [["paosberbank", 10360345]]}
Запрос 2: {"индикатор": "oshs_sub_tree_include_indicator", "режим": "circle", "company_name": "paosberbank", "company_unit_id_array": [["paosberbank", 10320279]]}
```

Для `fos` / `fg` пакет устроен как для `agile` (поле `unit_id_array`, элемент = число `ID`),
меняется только значение `индикатор`.

| `fact_count` (устаревшее имя метрики) | `hired_count` (актуальное имя) | `unknown-metric` |

**Ловушки фильтров (проверено, ошибка или пустота):**

Допустимые `type` узла фильтра — строго одно из: `condition` (`=`), `condition_in`
(`IN`/`NOT IN`), `condition_like` (`LIKE`/`ILIKE`), `condition_array` (`has`/`hasAny`),
`condition_null` (`IS NULL`/`IS NOT NULL`), `condition_param`. Типа `condition_not_null`
не существует — для «не равно NULL» используй `condition_null` с оператором `IS NOT NULL`,
иначе `«не распознан тип узла»`.

- **У `condition_in` поле `operator` ОБЯЗАТЕЛЬНО** и только `"IN"`/`"NOT IN"` (строкой, верхним
  регистром): `{"type":"condition_in","column":"unit_type","operator":"IN","value":["team"]}`.
  Без `operator` LO/MISSING → `filter-value-invalid` («отсутствует обязательное поле»);
- **У `condition_null` оператор — только `"IS NULL"` / `"IS NOT NULL"` ВЕРХНИМ регистром.**
  Строчные `"is not null"` → `filter-value-invalid` («регистр важен»);
- `condition_array` (`has`) — **только по Array-колонке** (`agile.unit_id`, `oshs_director_person_id`);
- `condition_like` — только по **строковой скалярной** колонке (`employee_full_name`,
  `position_name_top`). По массиву названий (`agile.unit_name`) падает —
  `LIKE/ILIKE работают только по строковой скалярной колонке`;
- у `condition_like` шаблон лежит в поле **`pattern`**, а не `value`;
- `segment`: `condition_in` по коду латиницей. `IN ["ТОП-600"]` (русское название) →
  пустой ответ, не ошибка;
- поиск структуры по названию в этой модели **не работает** — массивы названий не
  фильтруются подстрокой. Название → ID разрешается только через `get_structure_names_tool`
  или `org_structure`.

**Если нужной колонки нет в чертеже:** разрешается ОДИН вызов тулы `describe_model` по
`dm_core.employee_actual` (не больше), затем работай по его ответу. После 2 подряд
пустых/ошибочных запросов — раздел «ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА: СТРУКТУР НЕ НАЙДЕНО».

## Пагинация: общее правило для ВСЕХ запросов

Каждый ответ `mcp_query` содержит `limit`, `offset` и `has_next_page`. Правило
действует для ЛЮБОГО запроса этого скилла (шаги 1–3, все разрезы, Exp-1…Exp-4) и для
любого запроса скилла расчёта `get-involvement-metrics-by-unit-id` — независимо от
того, написано ли оно рядом с конкретным примером:

**Если `has_next_page: true` — продолжай сбор с `offset`.**
Увеличивай `offset` на использованный `limit` (остальные параметры те же) и повторяй
запрос, пока не получишь `has_next_page: false`. Не останавливайся на середине
выборки и не считай данные собранными, пока страница не последняя.

Запрос следующей страницы (вырос только `offset`) — это НЕ повтор из
«[ЗАПРЕТ НА ЗАЦИКЛИВАНИЕ]»: тот запрет — про вызовы с полностью идентичными
параметрами.

## Метрика численности — `hired_count` (НЕ использовать значения)

Все запросы к `dm_core.employee_actual` в этом скилле (шаги 1.3, «Разрез по
блокам», Exp-1, Exp-2) передают в `metrics` метрику численности — **`hired_count`**
(раньше имя было `fact_count`, оно устарело и возвращает `unknown-metric`).

**Метрика численности нужна технически** — чтобы сервер вернул строки с
`unit_id` и валидный ответ; без `metrics` запрос падает или возвращает пустоту.
Цель этих запросов — **собрать массив `unit_id`**, а не посчитать людей.

**Значения `hired_count` НЕ используйте ни в каком виде:**
- не выводите их пользователю;
- не суммируйте, не усредняйте, не агрегируйте между запросами/структурами;
- не сравнивайте численность структур между собой по этим числам;
- не опирайтесь на них при выборе режима (`single`/`circle`) или чеке лимита
  структур — число структур считайте по уникальным `unit_id`, а не по `hired_count`.

Числовой результат `hired_count` в этом скилле — технический побочный продукт,
не метрика вовлечённости и не отчётная численность. Сами метрики вовлечённости
считает скилл `get-involvement-metrics-by-unit-id` по модели `involvement_metric`,
где метрики численности нет вовсе.

## 1. Получение структуры

Результат шага — выбранная структура (`agile` / `oshs` / `fos` / `fg`), её ID
(и `company_name` для `oshs`).

**1.1 О ком идёт речь:**

Определи `person_id` руководителя. **По умолчанию это ВЫ САМИ** — в служебном блоке
системного промпта («Служебные данные текущего пользователя») уже есть строки `ФИО:` и
`person_id:`. Вопросы «моя команда», «мои команды», «под моим руководством», «в моей
команде» — это про ваш собственный `person_id`.

Порядок:

1. **Сам пользователь** («моя команда», «мои команды», «под моим руководством», без
   явного чужого ФИО) → бери `person_id` из служебного блока промпта и **сразу переходи
   к шагу 1.3, параллельно проверив сегмент этого же `person_id`** (см. триггер «Сегмент
   топ-600» выше). НЕ вызывай `search_persons_by_fio` — ФИО спрашивать не нужно, ответ
   уже есть в профиле. Если человек оказался топ-600 (`segment='top600'` + `is_director=1`)
   — уходи в «Разрез по сегменту (топ-600)» вместо обычного маршрута шага 1.3. Если в блоке
   есть ФИО — это же ваше ФИО.
2. **Явно назван ДРУГОЙ руководитель (ФИО в запросе)** — `person_id` получи по ФИО из
   `search_persons_by_fio` (поле `personUuid`). Не используй для этого
   `get_structure_names_tool`: он ищет только оргструктуры и персон НЕ возвращает.
   **В `search_persons_by_fio` передаётся только ФИО текстом — НЕ `person_id`, НЕ UUID.**
   Если ФИО пользователя не названо, вызывать этот тул нельзя.
   Сразу после получения `person_id` (своего или чужого) **проверь сегмент** человека
   в `employee_actual`: `segment = 'top600'` и `is_director = 1`. Если человек из топ-600 —
   переходи в раздел «Разрез по сегменту (топ-600)» (правило подсчёта там), а не в обычный
   шаг 1.3 «команды руководителя».
3. **ФИО не названо и нет название структуры** — попроси пользователя назвать ФИО или название команды:
   `Не удалось определить авторизованного пользователя. Назовите, пожалуйста, ФИО руководителя или название команды — определю состав и рассчитаю вовлечённость.`

Если пользователь назвал **название структуры** (не ФИО), а не себя — это шаг 1.2
(поиск структуры по названию), `person_id` для него не нужен.

**1.2 Если структура задана не явно (например, пользователь указал название команды):**
Используй тулу `get_structure_names_tool` для поиска структуры по названию.

Тула возвращает `structures[]` с полями `name`, `structure_type`, `hierarchy_kind`
(`agile` / `oshs` / `fg` / `fos` / `unknown`), `structural_level`, `db_filter`,
`warning`.Поля `unit_id` и деревьев у неё НЕТ: ID — это `db_filter.value`,
дерево названий — только из `dm_core.org_structure` (Exp-4).
`db_filter` — готовый фильтр для `mcp_query` по `<тип>.unit_id_tree` (например
`{"type":"condition_array","column":"oshs.unit_id_tree","operator":"has","value":63238876}`),
через него удобно проверять состав структуры.

**1.2.1 Если в запросе пользователя есть слово «блок»**

«Блок» = функциональный блок (`fblock_name` скалярный, НЕ agile-структура). **НЕ вызывай** `get_structure_names_tool` для поиска блока.

**Маршрут:**
1. Найди `fblock_code` через `ILIKE` по названию:
   ```json
   {
     "schema": "dm_core",
     "logic_model": "employee_actual",
     "columns": ["fblock_code", "fblock_name"],
     "filters": {
       "type": "condition_like",
       "column": "fblock_name",
       "operator": "ILIKE",
       "pattern": "%Люди и культура%"
     },
     "limit": 1
   }
   ```
2. Получив `fblock_code` → переходи к разделу **«Разрез по блокам»** (там сбор `oshs.unit_id` всех сотрудников блока).

**1.2.2 Тула вернула другие структуры (НЕ блок)**

Используй полученные `db_filter.value` для формирования запроса к `dm_core.org_structure` (Exp-4).

Тип иерархии из ответа (`hierarchy_kind`) — это и есть `<тип>` пакета. Если
пользователь назвал конкретную структуру — выбери подходящий элемент из
`structures[]` по совпадению `name` (и `structural_level`); при нескольких
кандидатах бери те, у кого `db_filter` не `None`. Для уровней ниже найденной
структуры ID определяется по `dm_core.org_structure` (Exp-4), а не по полям тулы.

Если `get_structure_names_tool` вернул ошибку, пустой `structures[]` или у всех
кандидатов `db_filter = None` — перейди к разделу «ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА:
СТРУКТУР НЕ НАЙДЕНО».

**1.3 Найди команды под руководством `person_id` (из шага 1.1)**

Для «моей команды / моих команд / под моим руководством» это **первое и обязательное
действие**: если `person_id` взят из служебного блока промпта — **вызови `mcp_query`
сразу**, не спрашивай ФИО и не вызывай `search_persons_by_fio`. ФИО пользователя у тебя
уже есть в служебном блоке.

Выполни `mcp_query` к `dm_core.employee_actual` с фильтром `has()` по колонке-директора.
Проверяй структуры в приоритете `agile → oshs → fos → fg`, пока не найдёшь непустой результат.

**Шаг 1.3-1 (agile):**
```json
{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["agile.unit_id"],
  "metrics": ["hired_count"],
  "filters": {
    "type": "and",
    "conditions": [
      {
        "type": "condition_array",
        "column": "agile_director_person_id",
        "operator": "has",
        "value": "<person_id_из_контекста>"
      }
    ]
  },
  "limit": 50,
  "offset":0
}
```
Если `agile.unit_id` ≠ `[]` — собери уникальные ID по правилу очистки (см. «Очистка ID
структур»), переходи к шагу 2.

**Шаг 1.3-2 (oshs):** Если agile пуст, вызови:
```json
{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["oshs.unit_id"],
  "metrics": ["hired_count"],
  "filters": {
    "type": "and",
    "conditions": [
      {
        "type": "condition_array",
        "column": "oshs_director_person_id",
        "operator": "has",
        "value": "<person_id_из_контекста>"
      }
    ]
  },
  "limit": 50,
  "offset":0
}
```
Если `oshs.unit_id` ≠ `[]` — собери уникальные ID по правилу очистки
(см. «Очистка ID структур»); `company_name` для пакета бери из константы
`"paosberbank"` (колонка `company_name` в `employee_actual` — не про `oshs`-компанию
модели `involvement_metric`), переходи к шагу 2.

**Шаг 1.3-3 (fos):** Если oshs пуст, вызови аналогично для `fos_director_person_id` → `fos.unit_id`.

**Шаг 1.3-4 (fg):** Если fos пуст, вызови для `fg_director_person_id` → `fg.unit_id`.

Пагинация у этих запросов — по общему правилу из раздела «Пагинация» выше.

**Шаг 1.3-5:** Если все 4 структуры вернули пустые массивы — перейди к разделу
«ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА: СТРУКТУР НЕ НАЙДЕНО».

## 2. Сборка параметрического фильтра (индикатор + массив ID)

Найденный уровень структуры, ID и (для `oshs` также `company_name`) станут параметрами
фильтра типа `condition_param` в скилле расчёта. Маппинг тип структуры → индикатор
(имя параметрической колонки в `involvement_metric`):

- `agile` → индикатор `agile_sub_tree_include_indicator`, поле `unit_id_array`, элемент = число `ID`;
- `oshs` → индикатор `oshs_sub_tree_include_indicator`, поле `company_unit_id_array`, элемент = пара `[company_name, ID]`;
- `fos` → индикатор `fos_sub_tree_include_indicator`, поле `unit_id_array`, элемент = число `ID`;
- `fg` → индикатор `fg_sub_tree_include_indicator`, поле `unit_id_array`, элемент = число `ID`.

Структурный индикатор — это **параметризованная колонка**, передаётся только через
`filters.type="condition_param"` (с `name` + `args` + `operator` + `value`), НЕ голым именем
в `columns` и НЕ через `param_columns`.

## ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА: СТРУКТУР НЕ НАЙДЕНО

Сюда попадаешь, когда поиск не дал результата: `get_structure_names_tool` вернул ошибку,
пустой ответ или пустые деревья (шаг 1.2), либо человек не руководит ни одной структурой
ни в одном из типов agile / oshs / fos / fg (шаг 1.3-5). Это штатный неудачный исход —
НЕ подменяй его случайным разрезом и не переходи к «Заметкам по разрезам».

Две ветки:

1. **Пользователь мог ошибиться в названии или структура существует, но не найдена** —
   попроси уточнить название:
   `Структура с таким названием не найдена. Уточните название команды (например, «Команда разработки X» или название отдела) — попробую найти её ещё раз.`
   Дождись ответа; при новом названии вернись к шагу 1.2.
2. **Пользователь подтвердил, что данных быть не должно** (человек не руководитель,
   структуры реально нет) — ответь с честным отказом:
   `По указанному человеку/структуре не найдено команд вовлечённости. Возможно, он не руководит командой или структура недавно переименована — уточните у руководителя.`

## [ЗАПРЕТ НА ЗАЦИКЛИВАНИЕ]

Не повторяй `mcp_query`/вызов `get_structure_names_tool` с одинаковыми параметрами.
Результат вызова уже в контексте чата: повторный вызов `get_structure_names_tool`
или `mcp_query` с теми же параметрами — то же нарушение.
**1 уникальный запрос → 1 вызов.**
Исключение — пагинация: запрос следующей страницы (тот же запрос, `offset` увеличен
на `limit` при `has_next_page: true`) повтором НЕ является, см. раздел «Пагинация».
После 2 пустых/ошибочных ответов подряд остановись и перейди к разделу
«ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА: СТРУКТУР НЕ НАЙДЕНО». Не перебирай фильтры вслепую
и не генерируй варианты подстановкой мусорных значений.

## [ЗАПРЕТ НА ВЫДУМЫВАНИЕ]

Запрещено подставлять заглушки (`1`, `0`, `None`, пустой массив) в ID структур пакета.
ID структур бери ТОЛЬКО из `employee_actual`, `org_structure` или
`get_structure_names_tool`. Если источник не дал ID — не компенсируй заглушкой:
иди в раздел «ПУСТОЙ РЕЗУЛЬТАТ ПОИСКА: СТРУКТУР НЕ НАЙДЕНО».

## Очистка ID структур - обязательно перед сборкой пакета

В `employee_actual` встречаются строки-мусор: `unit_id` = `0` или `null` вместе с пустым
`unit_name` / `unit_type`. Такой ID в `unit_id_array` гарантированно даёт пустую метрику.

Перед сборкой массива отфильтруй:

1. отбрось `unit_id`, равный `0`, `null` или пустой строке;
2. оставь уникальные ID, сохрани порядок.

Если после очистки массив пуст — это штатный «структур не найдено», см. «ПУСТОЙ РЕЗУЛЬТАТ
ПОИСКА: СТРУКТУР НЕ НАЙДЕНО». `0` и прочие заполнители в пакет НЕ попадают никогда.

Пример: `fg.unit_id` вернул `[0, 63670161]` → в пакет идёт только `63670161`.

## 3. Чек лимита структур и подтверждение

**Лимит действует ТОЛЬКО в режиме `circle`.** В режиме `single` количество структур не важно —
весь массив уходит одним запросом, подтверждение НЕ требуется (в т.ч. «Разрез по сегменту
(топ-600) целиком» и «Разрез по блокам» в `single` — там могут быть сотни ID, это нормально).

После сбора состава, если выбран режим **circle**, определи, сколько структур участвует в сравнении.

**≤5 структур** — не задавай лишних вопросов. Собери пакет (индикатор + массив ID в форме
режима + `company_name` для oshs) и передай в скилл `get-involvement-metrics-by-unit-id`
для расчёта в этом же ходе.

**>5 структур** — НЕ начинай расчёт немедленно. Спроси у пользователя подтверждение
долгого расчёта:

> Найдено N структур для сравнения. Расчёт займёт заметное время. Подтверждаете расчёт
> по всем N или укажите, пожалуйста, не более пяти конкретных структур для сравнения?

Если пользователь просит сократить — используй его состав. Соблюдай формулировку:
«Рассчитываю вовлечённость по одной структуре или подчинению конкретному руководителю.
Если есть время — готов запустить по всем N структурам; либо назовите, пожалуйста, не более
пяти структур для сравнения.»
Только после явного подтверждения пользователя переходи к расчёту через скилл
`get-involvement-metrics-by-unit-id`.

## Заметки по разрезам

### Разрез «по командам руководителя» 

Если вопрос — про вовлечённость по ВСЕМ командам руководителя («в разрезе команд»),
НЕ перебирай команды по одной. Получи список `agile.unit_id` из `employee_actual`,
затем сформируй пакет с индикатором `agile_sub_tree_include_indicator`.
Важно — если нет указания на компанию, нужно получить ответ по ВСЕМ командам этого руководителя.
Режим по умолчанию для этого разреза — `single` (`unit_id_array: [ID_1, ID_2, ...]`),
сравнение по каждой команде — режим `circle` (N запросов, каждый `unit_id_array: [ID_i]`)
и см. «Чек лимита структур и подтверждение (только в режиме **circle**)»: сообщи пользователю и жди подтверждения/сокращения состава.

### Динамика между волнами — НЕ поддерживается (сразу отказ, без сбора состава)

Вопрос про **изменение вовлечённости во времени** («выросла/упала», «динамика», «по сравнению
с прошлой/предыдущей волной», «в каких командах выросло/упало сильнее всего с прошлой волны»,
«прирост», «падение вовлечённости») — **не начинай сбор состава** и **не запускай circle**.
Динамика между волнами не реализована: доступна только актуальная волна
(`assignment_id = b870ba92-…`, см. скилл `get-involvement-metrics-by-unit-id`, «Динамика
между волнами — НЕ поддерживается»).

Эмуляция динамики перебором структур по текущей волне (как «выросло/упало по каждой
команде») — **запрещена**: это даёт сотни `mcp_query` без результата и виснет на десятки
минут. Сразу ответь одной фразой (формулировка — в скилле
`get-involvement-metrics-by-unit-id`, раздел «Динамика между волнами»).

### Общий вопрос без конкретики, чья команда - например «топ-N по компании», «где хуже всего»

Такой вопрос — это **сравнение по каждой структуре отдельно → режим `circle`** (не `single`:
нужен рейтинг структур, а не один агрегат по всем сразу).

1. Получи список всех `unit_id` из `dm_core.org_structure` (Exp-4) — там каталог типов
   (`tribe`/`cluster`/`team`/`fb_team`/`func_group`/`department`). **ВНИМАНИЕ: в `org_structure`
   колонки БЕЗ agile/oshs-префикса** — `unit_id`, `unit_name`, `unit_type`, `unit_id_tree`
   (НЕ `agile.unit_id_tree`/`oshs.unit_id_tree`, они есть только в `employee_actual`).
   Запрос с `agile.unit_id_tree` к `org_structure` → `unknown-column: maybe you meant 'unit_id_tree'`;
2. Отфильтруй нужный уровень (например `unit_type == "team"`);
3. Получи массив `unit-id`. Это сравнение по каждой структуре — **режим `circle`**
   (N запросов, каждый `unit_id_array: [ID_i]`).
4. **Сужение состава (обязательно, потому что `circle` — это много запросов).** Вопрос
   «топ-N по компании» на уровне всей компании подразумевает сотни/тысячи структур — это
   недопустимо долгий прогон. Прежде чем запускать `circle`, сузь состав и согласуй его
   с пользователем:
   - если из вопроса ясно **уровень** («трайбы», «кластеры», «команды») — используй его,
     на верхних уровнях структур заметно меньше;
   - если пользователь просит именно «где хуже всего / лучшие / топ-N» и размер выборки
     велик — **не запускай полный перебор**. Ответь: сколько всего структур найдено,
     предложи сократить (например, до N ≤ 5 конкретных, до одного уровня, или до
     одной команды) и дождись ответа. Формулировка:
     «Найдено N структур уровня «team» — сравнение по всем займёт очень долго.
     Уточните, пожалуйста, не более пяти конкретных структур, либо назовите уровень
     агрегации (трайб/кластер) — рассчитаю сравнение по ним.»
   - **никогда не сливай «где хуже всего» в режим `single`** молча — это даст один
     усреднённый показатель и потеряет смысл вопроса «где хуже».
5. После сужения состава запускай `circle` (для >5 структур — общий чек лимита из §3).
   Если пользователь явно просит **совокупный** показатель по набору структур — это уже
   режим `single` (`unit_id_array: [ID_1, ID_2, ...]`); выбор режима согласуй с пользователем,
   если из запроса это не очевидно.

### Разрез по сегменту топ-600

**Когда применять:** вопрос про конкретного человека топ-600 (ФИО / `person_id` /
должность) ИЛИ явное упоминание «топ-600 / TOP-600 / ТОП-600». После определения `person_id`
в шаге 1.1 проверь сегмент человека запросом к `employee_actual`
(`segment='top600'` + `is_director=1`). Если человек из топ-600 — расчёт по РУКОВОДИТЕЛЮ
топ-600 ведётся по правилу ниже, а НЕ через `agile_director_person_id`/`oshs_director_person_id`
(они у топов часто пустые или дают «команды», которых нет).

Сегмент топ-600 задаётся в `employee_actual` колонками `segment` и `segment_name`:
- `segment` — код на латинице, фильтровать по нему: `segment = 'top600'` (НЕ по русскому названию);
- `segment_name` = `«ТОП-600»` — только для отображения;
- руководитель сегмента помечен `is_director = 1`.

Чтобы получить вовлеченность по команде топ-600 (атрибуты уже лежат в строке человека из
проверки сегмента в шаге 1.1 — НЕ запрашивай отдельным запросом; правила проверяй СТРОГО
по порядку 1→4, не перескакивая):

1. Если `grade_level_position`=31 и в должности `position_name_top` упомянут **блок** —
   **выдели название блока из должности** и иди маршрутом шага 1.2.1 → «Разрез по блокам».
   Паттерн: в должности слово «блок»/«блока»/«блоке» с названием в кавычках рядом:
   «Руководитель блока "Люди и культура"» → блок «Люди и культура»;
   «Руководитель Управления по развитию команд блока "Технологии"» → блок «Технологии»;
   «ИО Руководителя блока "Sberbank International"» → блок «Sberbank International».
   Штатный `fblock_name` строки как «свой блок» НЕ используй: у руководителя блока он чаще
   «Руководство Банка» (`fblock_code`=12), а реальный блок человека написан только в должности.
   Названо несколько блоков («блоков "Риски" и "Люди и культура"») — обработай каждый,
   пакет с несколькими ID и объедини в один массив.
   Выделенное название подставь в шаг 1.2.1: `ILIKE` по `fblock_name` → `fblock_code` →
   «Разрез по блокам». Только `ILIKE`, не точное совпадение: название в должности может
   отличаться от справочника (в должности «Правовые вопросы, комплаенс и взаимодействие
   с госорганами», блок в справочнике — «GR, правовые вопросы, комплаенс и ДЗО»).
2. Если должность НЕ блочная, `grade_level_position`=31 и `fblock_code`=12 (Руководство
   Банка: Президент, руководители по направлениям В2В/В2С, старшие вице-президенты) —
   используй `unit_id` = 10000203 (ПАО Сбербанк).
3. Если `fblock_code`=36 (Руководство ТБ, включая подчиненные руководства в деревьях),
   то используй `unit_id` на уровень выше. Два примера:
   - Председатель СЗБ, его дерево ["ПАО Сбербанк", "Территориальные банки", "Северо-Западный банк",
     "Руководство территориального банка"] — нужно взять "Северо-Западный банк" — `unit_id` = 10086568;
   - Управляющий отделения Марий Эл, его дерево ["ПАО Сбербанк", "Территориальные банки",
     "Волго-Вятский банк", "Головные отделения на правах филиалов", "отделение Марий Эл № 8614",
     "Руководство"], нужно взять "отделение Марий Эл № 8614" — `unit_id` = 10016423.
4. Иначе используй `oshs.unit_id` этого человека.

Чтобы получить вовлечённость сегмента топ-600 целиком:
1. В `employee_actual` получи список `oshs.unit_id` всех руководителей сегмента
   (`segment = 'top600'` и `is_director = 1`);
2. Передай этот массив ID пакетом с индикатором `oshs_sub_tree_include_indicator`
   и режимом `single` (`company_unit_id_array: [[company_name, ID_1], [company_name, ID_2], ...]`).
   НЕ вызывай метрики по командам по отдельности. **Это режим `single`, поэтому лимит и
   подтверждение НЕ применяются** — даже если руководителей сегмента сотни, весь массив
   уходит одним запросом.

### Разрез по блокам

**Определение:** блок = функциональный блок (`fblock_name` — скалярная колонка в `employee_actual`).
**НЕ** agile-структура, НЕ `oshs.fblock_name`. В `dm_core.org_structure` функциональных
блоков НЕТ — блок ищется только через шаг 1.2.1, этот раздел — его продолжение.

**Маршрут (продолжение шага 1.2.1, других способов поиска блока нет):**
1. `fblock_code` уже получен в шаге 1.2.1.
2. Собери `oshs.unit_id` этого блока — **по всем сотрудникам блока, БЕЗ фильтра
   `is_director`** (важно получить ВСЕ уникальные `unit_id`, даже структур без руководителя):
   ```json
   {
     "schema": "dm_core",
     "logic_model": "employee_actual",
     "columns": ["oshs.unit_id"],
     "metrics": ["hired_count"],
     "filters": {
       "type": "and",
       "conditions": [
         {"type": "condition", "column": "fblock_code", "operator": "=", "value": <fblock_code>}
       ]
     },
     "limit": 200,
     "offset": 0
   }
   ```
3. Если `has_next_page: true` — продолжай сбор с `offset` (общее правило «Пагинация»).
4. **Пустой результат → fallback:** `condition_like` с `ILIKE` по `fblock_name` (возможно,
   пользователь неточно назвал блок) — тоже **по всем сотрудникам блока, БЕЗ `is_director`**:
   ```json
   {
     "schema": "dm_core",
     "logic_model": "employee_actual",
     "columns": ["oshs.unit_id"],
     "metrics": ["hired_count"],
     "filters": {
       "type": "and",
       "conditions": [
         {"type": "condition_like", "column": "fblock_name", "operator": "ILIKE", "pattern": "%<название>%"}
       ]
     },
     "limit": 200,
     "offset": 0
   }
   ```
5. Собери уникальные `oshs.unit_id` (очистка: `0`/`null` отбрось).
6. Режим по умолчанию — `single` (совокупный показатель по блоку, лимит не действует).
   Если нужен сравнительный разрез по структурам блока — режим `circle`, тогда при >5
   структурах см. «Чек лимита структур»: запрос подтверждения.
7. Пакет: `oshs_sub_tree_include_indicator` + `company_unit_id_array`.

### Уровни оргструктуры (маппинг терминов)

- `трайб` / `кластер` / `команда` — agile-уровни: `agile.level_1_unit_id` = трайб,
  `agile.level_2_unit_id` = кластер, `agile.level_3_unit_id` = команда (названия — в
  `agile.level_N_unit_name`). Колонок `agile.level_1` / `level_2` / `level_3` (без суффикса
  `_unit_id`) НЕ существует — запрос с ними падает с `unknown-column`. Это массивы, фильтр — только `has`;
  у некоторых сотрудников `agile.level_3_unit_id` = `[null]` — такие строки отбрасывай;
- `функциональный блок` — `fblock_name` (скаляр, `Nullable(String)`) для линии «кто в блоке» и
  `oshs.fblock_name` (`Array(String)`) для группировки по блоку. Колонки `agile_fblock_name`
  НЕТ ни в `employee_actual`, ни в `org_structure`; `oshs_fblock_name` и `fb_name` не
  существует нигде — блок по линейной структуре это `oshs.fblock_name`, по agile — `fblock_name`.
  Не фильтруй блок по agile-колонкам. `fblock_code` — числовой код блока, а не название;
- `сегмент` — `segment` (код на латинице, напр. `digital`, `profi`, `top600`) / `segment_name` (русское название).

Слова «дивизион» в данных нет — не выдумывай этот уровень. «Дивизион» и прочие нестандартные
уровни уточняй по `unit_type` в `org_structure` (Exp-3), не подставляй вслепую. «Блок» —
исключение: функциональный блок ищется
только маршрутом 1.2.1 + «Разрез по блокам» (`fblock_name`), `org_structure` для блока НЕ используется.

**НЕЛЬЗЯ показывать пользователю внутренности запроса.** Никакие UUID (`index_id`, `group_id`,
`person_id`), технические заголовки из тулов и `unit_id` в ответе НЕ выводи.

## Примеры задействованных запросов (справочно)

### **Exp-1** — `mcp_query` к `dm_core.employee_actual`: уникальные `unit_id` по колонке-директору (`<тип>_director_person_id`).

Проверь структуры в приоритете `agile → oshs → fos → fg`, фильтр по колонке-директору
оператором `has` по `person_id`. Пример для `agile` (для `oshs`/`fos`/`fg` меняются только
`column` директора и колонка результата):

{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["agile.unit_id"],
  "metrics": ["hired_count"],
  "filters": {
    "type": "and",
    "conditions": [
      {
        "type": "condition_array",
        "column": "agile_director_person_id",
        "operator": "has",
        "value": "d2c78d8f-e062-41a0-8000-0feaa886f996"
      }
    ]
  },
  "limit": 200,
  "offset":0
}

Этот запрос вернёт строки, где человек — руководитель (`has` по массиву директоров),
и собери **уникальные** `agile.unit_id` по правилу «Очистка ID структур» (`0`/`null` не берём).
Аналогично для `oshs`/`fos`/`fg` с их колонками
`<тип>_director_person_id` и `<тип>.unit_id`; `company_name` для пакета всегда константа
`"paosberbank"` (из `employee_actual` его не берём).
Берётся первая структура с непустым результатом по приоритету выше.
Пагинация — по общему правилу «Пагинация» в начале скилла.

### **Exp-2** — `mcp_query` к `dm_core.employee_actual`: уникальные `unit_id` по функциональному блоку (`fblock_code`).

{
  "schema": "dm_core",
  "logic_model": "employee_actual",
  "columns": ["oshs.unit_id"],
  "metrics": ["hired_count"],
  "filters": {
    "type": "and",
    "conditions": [
      {
        "type": "condition",
        "column": "fblock_code",
        "operator": "=",
        "value": 18
      }
    ]
  },
  "limit": 200,
  "offset":0
}

Этот запрос вернёт строки, где каждый `unit_id` относится к указанному в filters функциональному блоку `fblock_code`. Собери **уникальные** `unit_id` по правилу «Очистка ID структур» (`0`/`null` не берём).
Пагинация — по общему правилу «Пагинация» в начале скилла.

### **Exp-3** — `mcp_query` к `dm_core.org_structure` с `metrics: ["unit_count"]` по `unit_type` (каталог типов уровней).

{
  "schema": "dm_core",
  "logic_model": "org_structure",
  "columns": ["unit_type"],
  "metrics": ["unit_count"],
  "limit": 50,
  "offset": 0
}

Возвращает распределение всех типов подразделений, например:
`tribe`, `cluster`, `team`, `fb_team`, `func_group`, `department`.

### **Exp-4** — `mcp_query` к `dm_core.org_structure` по `unit_id`/`unit_name`/`unit_type` (+ деревья) — список команд.

{
  "schema": "dm_core",
  "logic_model": "org_structure",
  "columns": ["unit_id", "unit_name", "unit_type", "unit_id_tree", "unit_name_tree", "unit_type_tree"],
  "limit": 50,
  "offset": 0
}

`company_name` по умолчанию равен `"paosberbank"`. Если увидишь `"company_name": "ПАО Сбербанк"`
замени на `"company_name":"paosberbank"` — только так работает модель `involvement_metric`.
