# Контракт

Вход: person_id выбранного руководителя, подтверждённый доступ, четыре пары
quarter_start/quarter_end, выбранная структура ОШС либо Agile (по умолчанию ОШС). Показатели доступны по записи руководителя.
person_id — personUuid выбранной и подтверждённой записи HR Search,
переданный lookup_employee_by_name. Не табельный номер.
Фильтры employee_status и oshs.fact_flag не добавлять в исторический запрос:
условия расчёта фактической численности заданы в метриках датасета.
Не выбирать подчинённых и не вычислять показатели вручную.

# Каталог: семь показателей, в одном разборе только четыре

| Имя | Смысл | Вызов |
|---|---|---|
| one_to_one_coverage_pct_oshs | Охват встречами 1:1, ОШС, % | param_metrics |
| one_to_one_coverage_pct_agile | Охват встречами 1:1, Agile, % | param_metrics |
| manager_assigned_learning_pct_oshs | Назначено обучение, ОШС, % | param_metrics |
| manager_assigned_learning_pct_agile | Назначено обучение, Agile, % | param_metrics |
| experienced_employees_agile | Доля сотрудников со стажем от 6 месяцев, Agile, % | metrics |
| experienced_employees_oshs | Доля сотрудников со стажем от 6 месяцев, ОШС, % | metrics |
| is_mentor_or_coach | Признак ментора/коуча, 0 или 1 | metrics |

Для двух выбранных param_metrics обязательны оба аргумента типа Date: period_start и
period_end, строки YYYY-MM-DD. Для двух выбранных metrics таких аргументов нет.
Шесть долей каталога уже в шкале 0–100. Признак ментора не процент.
Назначенное обучение не означает пройденное обучение; бейдж не измеряет качество
коучинга; доля опытных сотрудников не измеряет результативность их работы.

# Выбор одного набора

ОШС: experienced_employees_oshs, is_mentor_or_coach,
one_to_one_coverage_pct_oshs, manager_assigned_learning_pct_oshs.
Agile: experienced_employees_agile, is_mentor_or_coach,
one_to_one_coverage_pct_agile, manager_assigned_learning_pct_agile.
Не запрашивай обе структуры в одном проходе. Не переносись на Agile из-за NULL в ОШС.
Показатели невыбранной структуры не считаются отсутствующими: они не запрашивались.
Ниже основные шаблоны для ОШС, затем полные альтернативные шаблоны для Agile.
Выбери ровно одну пару шаблонов: первый один раз, второй четыре раза.

# Выполнение: пять запросов

Используй конкретные даты из списка кварталов, переданного агентом.
Шаблоны содержат заполнители: замени их перед отправкой. Фильтр person_id
одинаков во всех пяти запросах. Не смешивай две группы в одном запросе.

## 1. Один запрос обычных метрик за четыре квартала

FIRST_QUARTER_START — первый день самого раннего квартала;
LAST_QUARTER_END — последний день самого позднего завершённого квартала.
На 22.10.2026 диапазон: 2025-10-01–2026-09-30.
Ожидаются 2025-12-31, 2026-03-31, 2026-06-30, 2026-09-30.

```json
{
  "schema": "dm_core",
  "logic_model": "employee_hist",
  "columns": [
    "report_date"
  ],
  "metrics": [
    "experienced_employees_oshs",
    "is_mentor_or_coach"
  ],
  "filters": {
    "type": "condition",
    "column": "person_id",
    "operator": "=",
    "value": "<PERSON_ID>"
  },
  "time_dimensions": [
    {
      "name": "report_date",
      "granularity": "quarter_end",
      "range": {
        "type": "absolute",
        "from": "<FIRST_QUARTER_START>",
        "to": "<LAST_QUARTER_END>"
      },
      "fill": {
        "mode": "previous"
      }
    }
  ],
  "limit": 100
}
```

## 2. Четыре запроса параметрических метрик

Выполни шаблон отдельно для каждого квартала:

| Квартал на дату примера 22.10.2026 | period_start | period_end | day: from = to |
|---|---|---|---|
| IV 2025 | 2025-10-01 | 2025-12-31 | 2025-12-31 |
| I 2026 | 2026-01-01 | 2026-03-31 | 2026-03-31 |
| II 2026 | 2026-04-01 | 2026-06-30 | 2026-06-30 |
| III 2026 | 2026-07-01 | 2026-09-30 | 2026-09-30 |

Даты рассчитываются относительно даты обращения; не закрепляй этот пример навсегда.
period_start/period_end ограничивают даты событий внутри массивов встреч/обучения.
Временной срез берётся на конец того же квартала (day, одинаковые from/to).
Это не запрос на сегодняшний день и не диапазон ежедневных срезов всего квартала.

```json
{
  "schema": "dm_core",
  "logic_model": "employee_hist",
  "columns": [
    "report_date"
  ],
  "param_metrics": [
    {
      "name": "one_to_one_coverage_pct_oshs",
      "args": {
        "period_start": "<QUARTER_START>",
        "period_end": "<QUARTER_END>"
      }
    },
    {
      "name": "manager_assigned_learning_pct_oshs",
      "args": {
        "period_start": "<QUARTER_START>",
        "period_end": "<QUARTER_END>"
      }
    }
  ],
  "filters": {
    "type": "condition",
    "column": "person_id",
    "operator": "=",
    "value": "<PERSON_ID>"
  },
  "time_dimensions": [
    {
      "name": "report_date",
      "granularity": "day",
      "range": {
        "type": "absolute",
        "from": "<QUARTER_END>",
        "to": "<QUARTER_END>"
      },
      "fill": {
        "mode": "previous"
      }
    }
  ],
  "limit": 100
}
```

Две параметрические метрики выбранной структуры можно объединить, потому что у них одинаковые
person_id, аргументы квартала и дата/шаг среза. Обычные метрики идут отдельно.
Если группа обычных метрик падает, допустимо один раз разделить её на отдельные
метрики для локализации ошибки, сохранив UUID и период. Не повторяй неизменный
падающий запрос. Например, ошибка last_hire_date не доказывает неисправность
is_mentor_or_coach. Аналогично можно выделить неисправную параметрическую метрику.

# Результат и ошибки

Сопоставляй возвращённые значения с именами метрик по метаданным ответа, не по
порядку столбцов. Если сервер использует неизвестные имена результатов param_metrics,
не угадывай соответствие: сохрани диагностическую ошибку и уточни контракт ответа.
Ожидаются четыре конца квартала в запросе обычных метрик и ровно одна дата
конца соответствующего квартала в каждом запросе параметрических метрик. Дубликаты не усреднять, неожиданные даты
не исправлять молча. Неполную выдачу дочитай поддерживаемой пагинацией.

Верни для каждой пары metric/quarter значение либо статус missing, error или invalid,
фактическую report_date, границы периода и доступные сведения о fill.
Пустая выдача и NULL означают отсутствие данных, не 0. Ноль — полноценное значение.
Значения долей вне 0–100 и бейдж не из {0,1} не интерпретировать; сообщить о качестве.
При ошибке конкретной метрики допустимо отдельно повторить запрос остальных метрик
того же квартала с неизменными фильтром и датами. Не расширять доступ и выборку.
Никакие ошибки не заменять числами из примеров, старого чата или прошлых кварталов.
fill: previous принадлежит серверному историческому механизму. Если он не сообщает
происхождение точек, нельзя утверждать, что каждая точка — новое независимое измерение.

# Передача в интерпретацию

Передай четыре выбранных показателя, включая полностью отсутствующие: для каждой
из четырёх дат значение и статус. Нормы не являются аргументами MCP и не меняют SQL.
Их применяет manager_efficiency_insight после получения данных.

# Контроль вызова

JSON-шаблон передавай непосредственно аргументами mcp_query, без внешней обёртки.
Поле columns обязательно сохрани непустым. Для показателей сохраняй также metrics
или param_metrics и time_dimensions. Не используй parameters вместо param_metrics.
При query-empty перечитай шаблон и исправь выбранные поля; допускается только одна
исправленная попытка, после повторной ошибки остановись. Не меняй лишь limit или фильтр.

# Завершение получения данных

После пяти успешных запросов переходи к интерпретации. Не отправляй шестой
запрос к истории «для проверки», не ищи сотрудника повторно из-за NULL.
Дополнительные вызовы допустимы только по описанным правилам исправления ошибок
или необходимой пагинации. Не увеличивай число вызовов ради служебного лога.
Техническую матрицу значений, статусы и полные даты не выводи пользователю.
Сохрани их в контексте для интерпретации; диагностический код независимо
фиксирует полученные значения и вычисляет разности в журнале сервера.

# Передача результата для инсайта

После получения данных не публикуй матрицу или промежуточный отчёт пользователю.
Сохрани ответы инструментов в контексте и перейди к manager_efficiency_insight.
Служебные проверки и пропуски предназначены для существующей Python-диагностики.

```json
  "columns": [
    "report_date"
  ],

    "experienced_employees_agile",
    "is_mentor_or_coach"
  ],
  "filters": {
    "type": "condition",
    "column": "person_id",
    "operator": "=",
    "value": "<PERSON_ID>"
  },
  "time_dimensions": [
    {
      "name": "report_date",

        "mode": "previous"
      }
    }
  ],
  "limit": 100
}
```
